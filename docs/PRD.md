# BrandPulse 产品需求文档（v0.2）

## 1. 产品背景

品牌团队需要持续跟踪新闻、公开 RSS 和用户反馈，及时识别产品质量、服务与声誉风险。单纯依靠人工监控容易漏报，通用大模型直接生成处置建议又可能编造企业内部政策。

BrandPulse 将公开舆情采集、可靠异步分析和品牌内部知识检索组合成可演示、可测试、可追踪的闭环。

## 2. 目标用户

- 品牌市场与公关人员
- 客服和售后团队
- 舆情分析与风险管理人员

## 3. 产品目标

系统需要完成以下主链路：

```text
手工录入 / RSS 自动采集
  → 内容指纹去重
  → 持久化分析任务与 Redis 可靠队列
  → 品牌知识向量召回
  → 大模型证据充分性审核
  → 知识增强的结构化舆情分析
  → 风险概览、趋势和引用依据展示
```

核心原则：

1. 采集与分析解耦，外部模型变慢或限流时不阻塞文章入库。
2. 任务状态、失败原因和分析结果必须持久化并可恢复。
3. 企业事实只能来自审核通过的品牌知识，不能由分析模型自行补全。
4. 所有效果和性能指标必须来自可复现实验。

## 4. 当前版本范围

### P0：已完成的核心闭环

1. 品牌创建、列表和详情查询。
2. 手工录入文章与公开 RSS Feed 导入。
3. RSS 数据源持久化、立即采集、启停、采集周期和单轮文章上限。
4. 独立 Collector 定时采集，到期数据源自动拉取、去重并提交分析。
5. SHA-256 内容指纹去重。
6. OpenAI-compatible LLM Provider 和 Pydantic 结构化输出。
7. PostgreSQL 持久化任务、结果与错误信息。
8. Redis pending/processing 可靠队列、原子领取、确认、失败重试和启动恢复。
9. 同一文章活动任务复用及数据库并发约束。
10. 品牌风险概览、高风险文章列表和近 30 天趋势。
11. React + TypeScript 管理台及自适应任务轮询。
12. Docker Compose 一键运行前端、API、迁移、worker、collector、PostgreSQL 和 Redis。
13. 后端测试、静态检查、前端检查和 GitHub Actions CI。

### P1：已完成的知识增强分析

1. PostgreSQL + pgvector 品牌知识库。
2. UTF-8 Markdown 按章节分块、向量化和按来源替换入库。
3. OpenAI-compatible Embedding Provider，当前向量维度固定为 1024。
4. 按品牌隔离的余弦相似度 Top K 检索。
5. Evidence Judge 对候选文本执行证据充分性审核。
6. 只向最终舆情分析模型注入审核通过的知识块。
7. 分析结果记录知识来源、章节、相似度、Embedding 模型、审核模型和审核原因。
8. 前端区分“使用品牌知识”和“未使用品牌知识”，并展示引用依据。
9. 检索评测集、命令行评测工具及正负对照实验记录。

### P2：待实现的增强能力

1. TXT、HTML 和 RSS 正文清洗及统一知识入库管线。
2. 重排序模型、更大规模检索评测和模型成本对比。
3. OpenClaw/Agent 日报生成与高风险消息推送。
4. 鉴权、角色权限和多租户隔离。
5. 在线演示环境、SSE/WebSocket 实时进度和生产部署配置。
6. CSV 批量导入、更多网页数据源和前端端到端测试。

## 5. 功能需求

### 5.1 舆情采集

- 用户可以手工创建文章并关联品牌。
- 用户可以为品牌保存多个 RSS 数据源。
- Collector 根据数据源的采集间隔自动执行采集。
- 每个数据源可以设置单轮最多处理的文章数，避免 Feed 突然产生大量模型任务。
- 重复正文不能重复写入数据库。

### 5.2 异步分析

- API 创建持久化任务后将任务 ID 写入 Redis pending 队列。
- worker 必须使用原子操作将任务移动到 processing 队列。
- 成功任务写入结构化结果并从 processing 队列确认删除。
- 失败任务记录尝试次数和错误；达到上限后标记为 failed。
- worker 重启时恢复中断任务，提供 at-least-once 处理语义。

### 5.3 品牌知识与 RAG

- 每个知识块必须关联品牌、来源文件、章节和分块序号。
- 文档入库时调用 Embedding Provider 并保存 1024 维向量。
- 分析文章时，系统根据标题和正文构造查询，在对应品牌内召回候选知识。
- Evidence Judge 只能依据候选文本判断证据是否充分，不得使用外部知识补全。
- 证据不足时仍可进行一般舆情分析，但不得编造产品参数、内部规则、响应时限或企业政策。
- 证据充分时，只注入审核模型选中的支持文本块。

### 5.4 结果展示

- 展示情感、情感分数、风险等级、风险分数、风险类型、摘要和处置建议。
- 展示异步任务的排队、处理、完成和失败状态。
- 展示是否使用品牌内部知识。
- 使用知识时展示来源、章节和相似度；未使用时展示证据不足原因。
- 前端在存在活动任务时提高轮询频率，空闲时降低频率。

## 6. 非功能需求

- 可恢复：Redis 短暂不可用或 worker 退出后，持久化任务能够重新分发。
- 可观测：worker 日志包含 `job_id`、`article_id`、尝试次数、Provider 和知识使用状态。
- 可测试：外部 RSS、LLM 和 Embedding 调用可以使用测试替身隔离。
- 可配置：模型地址、模型名、超时和重试次数通过环境变量配置。
- 可部署：开发者可以使用 Docker Compose 启动完整系统。
- 安全：真实 API Key 和 `.env` 不得提交到仓库。

## 7. 验收场景

### 场景 A：知识命中

1. 用户为 BlueCurrent 创建一篇包含 `BC-D200` 和 `SEAL-07` 的文章。
2. API 返回 `202 Accepted` 并创建异步任务。
3. worker 完成向量检索、证据审核和结构化分析。
4. 结果正确引用 `SEAL-07` 首次操作及用户处置政策。
5. 前端显示“已使用品牌内部知识”及引用文本块。

### 场景 B：范围外内容

1. 用户创建一篇询问 BlueCurrent 手机电池保修期限的文章。
2. pgvector 可以返回语义相近候选，但 Evidence Judge 判定证据不足。
3. 系统不向最终模型注入无关内部知识。
4. 前端显示“未使用品牌内部知识”和拒绝原因，结果不编造保修期限。

### 场景 C：RSS 自动采集

1. 用户保存并启用公开 RSS 数据源。
2. Collector 按配置间隔采集，且单轮处理数量不超过数据源上限。
3. 新文章自动入库并进入分析队列，重复文章被跳过。
4. worker 最终完成分析，前端轮询后展示新结果。

### 场景 D：故障恢复

1. worker 领取任务后异常退出。
2. worker 再次启动时把 processing 中断任务恢复到 pending。
3. 任务重新执行并最终进入 completed 或达到上限进入 failed。

## 8. 评测指标

当前已经建立的可复现指标：

- 可回答问题 Top 1 命中率。
- 可回答问题 Top 3 命中率。
- 范围外问题拒绝率。
- 正确证据排名与余弦相似度。
- 端到端分析是否使用知识及引用数量。

当前演示评测包含 8 个可回答问题和 2 个范围外问题。知识卡优化后，纯向量检索 Top 1 为 `7/8`，Top 3 为 `8/8`；Evidence Judge 的 Q2、Q9、Q10 三条冒烟用例均符合预期。详细实验记录见 [`evaluation/pgvector_retrieval_evaluation.md`](evaluation/pgvector_retrieval_evaluation.md)。

后续需要补充：

- 更大评测集上的检索与拒答指标。
- 情感分类和风险类型准确率。
- API P95 响应时间及队列吞吐量。
- 单条分析耗时、Token 用量和模型成本。

## 9. 非目标

- 绕过验证码、登录限制或网站反爬机制。
- 未经授权采集个人信息或非公开数据。
- 在当前版本构建大规模分布式爬虫。
- 自训练基础大模型。
- 把 AI 输出直接作为正式公关或安全决策，不经过人工复核。
